# An optional backend: guests stay offline-only, and a signed-in Organizer's Account is the source of truth

ADR-0001 made the app client-only and named the condition for revisiting it: a backend "when the app needs shared, multi-user data". That condition has arrived, but not as multi-user collaboration. It arrived as **durability and cross-device access**: an organizer's season of rosters lives in one browser profile, clearing site data is indistinguishable from a fresh install, and the same roster cannot exist on a laptop and a phone. We are therefore adding an **optional** backend. A guest keeps today's behaviour exactly: everything local, no account, no network. Signing in makes the Account's data **authoritative** — it lives on a server, so it survives a lost device, a new browser and a second device, and an edit made on one device is visible on the others.

The offline promise is unchanged for everyone, including a signed-in Organizer, and the two hold together because **authority is not the read path**. Authority lives on the server. The read path stays IndexedDB: the device keeps a write-through cache, so opening the app never waits on the network and a signed-in Organizer on a court with no signal sees their roster rather than an error. When the network returns, the cache is refreshed from the server, and a write made while offline is pushed — and **rejected, with a message**, if another device changed that Community first.

**This corrects an earlier draft of this ADR, which chose the reverse** and made the server a copy rather than the source of truth. Its reasoning was that server-authoritative reads break the offline promise. That is right about the failure and wrong about the remedy: the promise breaks if the *read path* depends on the network, not if the *server* is authoritative. Keeping IndexedDB as a cache-through read path satisfies both at once. The genuinely worse alternative — discarding an offline edit rather than reconciling it — is rejected below.

**Status**: accepted

**Supersedes**: ADR-0001, which stays in the record as the reasoning for the client-only phase and remains accurate for guests.

**Considered Options**:

- **No backend; make export/import the whole durability story** (the ADR-0001 position, and ticket 34's). A file the organizer owns is a real durability story, but it cannot put the same roster on two devices, and every export is a manual step a tired organizer skips. Ticket 34 still ships: it is the *guest's* story, and browser eviction remains a guest's failure mode.
- **Server-authoritative once signed in, with call-through reads** (rejected, and it is the reason the chosen option is worded the way it is). Every `list*()` hits the API and the local store is a guest-only cache. This is the version that genuinely breaks the offline promise: a signed-in Organizer on a court with no signal, or with a token that expired an hour ago, opens an app with nothing in it. The problem is the *read path*, not the server's authority — so the chosen option below keeps the authority and changes the read path.
- **An anonymous sync key instead of an account** (a long code typed on the second device; no auth at all). Rejected: it cannot recover a lost device, which is the failure the feature exists to fix, and it forecloses the identity model the passkey/Google decision requires.
- **Per-record server sync** (every `savePlayer`/`deleteSquad` becomes an API call, with tombstones and per-record merge). Rejected for the first cut: the client has no `updatedAt`, `deletedAt` or revision field on any entity, so there is nothing to merge on, and the seam already speaks whole-collection terms (`replaceAllPlayers` and its four siblings are atomic-overwrite operations that exist today).
- **Optional accounts, local-first for a guest and server-authoritative for a signed-in Organizer** (chosen). The two are not in tension, because the guest has no server copy to be authoritative about, and a signed-in Organizer's read path is a cache that the device already knows how to maintain.

Rejected in favour of the option above: **strict server authority, where an edit made offline is never pushed and the client refetches and discards on reconnect.** It is simpler and completely honest, and it is still wrong here: it silently drops the organizer's offline edits, which is the opposite of what an account is for.

**Consequences**:

- **Disciplines become account data, and the backup must carry them.** The catalog is global today (`BackupData` has no `disciplines` field, so a custom Discipline is lost on export/import, and `useDisciplines` re-seeds the built-ins whenever the list reads back empty). A per-account catalog is impossible to sync without a `disciplines[]` array and a `version: 5` migration, so closing that gap is a prerequisite of this feature, not a follow-up.
- **`Player` gains `createdAt`.** "Recently added" is currently *physical order*: `list()` is a bare `getAll()` with no index, `useRoster` applies no sort, and the Dashboard takes `players.slice(-3)`. A server answers in whatever order it likes, so the roster's meaning has to be expressed rather than inherited from a storage engine's iteration order.
- **The storage seam does not change shape, and that is what makes the authority move affordable.** Every `list*()` takes no arguments and returns every row in the database, and community scoping happens by filtering in the React layer rather than in the store. That stays true: a Community's collections are replaced wholesale, which is what `replaceAllPlayers` and its four siblings already exist to do, and the server learns which Account is asking from the token rather than from the payload. This is why the guidance in ticket 25 ("Do not push filtering into the store") survives a backend, and why the store interface gains no tenant argument. What the seam *does* gain is a caller written by this feature, and that caller must be the only thing that talks to the network. Six screens, zero `list*()` call sites change; the seam stays a cache's interface rather than becoming the app's window onto the server.
- **The wire format is the backup format.** One JSON document per `(account, community)`, reused for both export and sync, with a version integer. Reusing it means no merge algorithm, no second schema and no duplicated validation: `serializeBackup`/`parseBackup` already encode, validate and migrate this payload, including the rule that adopts orphaned records.
- **Nothing is normalized.** No server-side querying, no foreign keys. This is deliberate: Player deletion leaves dangling ids in `poolPlayerIds`, `result.teams[].slots[].playerId` and `matches[].teamAId` on purpose, tolerated at read time by a single filter. A normalized schema with real foreign keys would reject what the app deliberately does.
- **A write is server-first, whole-community, debounced and versioned.** A write made while signed in does not become visible to another device until the server has accepted it, and a stale push is rejected rather than applied, so device B cannot silently erase device A's evening. Last-write-wins at community granularity without a version would be undetectable data loss, and the client has no field to detect it with.
- **First sign-in adopts local data.** If the account has never synced, the device's existing records become the account's initial state, behind a confirm when the local roster is non-empty. Replacing local data unconditionally would delete a guest's roster at the moment they sign in.
- **Token expiry never clears local data; only explicit logout does.** Clearing on expiry would hand a signed-in organizer an empty app on a court with no signal. The consequence is accepted: a device with a dead token keeps readable data, so logout is the only destructive control, and it must be explicit and confirmed.
- **Nothing may push while signed out.** Logout empties the local stores, and the hooks immediately want to write again (the roster's orphan-repair effect in particular). The "who owns this write" guard belongs at one boundary, not scattered across call sites.
- **A sign-in must never overwrite a server that has already synced.** The rule "first sign-in on an Account that has never synced adopts the device's records" was written when a bad overwrite could only damage the local copy. It is now the one path in the whole feature that can destroy the authoritative copy, so the guard is on the *account's* state and not on the device's: an account with existing server state is fetched and rendered, and the device's records are only ever offered as a deliberate choice, never applied automatically. A device holding guest data that signs into an already-populated account is the exact case that must be safe by default.
- **A pending offline write blocks sign-out, or is discarded with an explicit confirm.** Signing out empties the local stores, and a write queued while offline has nowhere to go once they are gone. Under the old model this was a lost local edit; now it is a lost authoritative edit, and it is lost silently unless something refuses. Sign-out must not clear a store that has an unpushed write, and the confirm names what is being given up.
- **A cache being served while the account cannot be reached is shown as a cache.** Token expiry deliberately keeps the data readable (`PRODUCT.md`: a signed-in organizer on a court must not find an empty app). That was defensible when the device was a peer. It is not defensible now without a signal, because an organizer recording tournament results into a stale cache and believing they are saved is the failure this whole decision makes more likely. The UI names the state whenever it is rendering a copy it could not refresh.
- **A rejected offline write is never dropped quietly.** When the server refuses a queued write because another device moved the same Community, the Organizer is shown what would be lost — which Communities, and when they were last changed elsewhere — and chooses: keep the server's version, or push the device's over it deliberately. A silent discard here is the one failure this design cannot have, because the person losing the data is offline at the time and will not see the conflict arrive.
- **The cache is never read as truth about who owns a record.** A device that signs out stops being authoritative immediately: the caches are emptied, and the guards that stop the hooks writing again afterwards ("nothing may push while signed out") are what keep a signed-out device from quietly re-seeding itself as a guest roster.
- **Guest data has no server copy, and the app must say so.** Signing out clears the account's data from the device. A guest who never signs in remains exposed to browser eviction until ticket 34 ships, and no amount of backend work changes that.
- **One origin is canonical.** Whatever identity mechanism ships, the app's origin is its Relying Party ID, so the production hostname must be settled before any credential is registered. `wrangler.jsonc` currently carries `"name": "comp3tive"` as a documented placeholder.
- **The app stays on Cloudflare's static-assets Worker and the API joins it under `assets.run_worker_first`.** `/api/*` is the address ADR-0006 reserved, and the Worker answers it while continuing to serve the two documents from `./dist`. Two consequences that would otherwise bite silently. **First:** the deploy's `compatibility_date` (`2026-09-14`) is past the 2025-04-01 threshold where a navigation request does not invoke the Worker script even when the path matches, so without `assets.run_worker_first: ["/api/*"]` a `fetch()` would reach the API while a browser navigating to that path would be served HTML — the fix is config, and it must be in the same change that adds the route. **Second:** the static-assets router does not pass `ctx.access` to the user Worker, which is one more reason Access is not the identity layer (below).
- **Cloudflare Access is not the sign-in, and this is a decision rather than an omission.** Access is an identity-aware gate for a known set of people: every request is denied unless it matches an Allow policy, users are added to policies by hand, and there is no self-service registration flow, no user directory, and no per-user data model to attach an Account to. Its free tier is also capped by seat count, which a public consumer app would exceed. What it *is* good at — a gate in front of an internal or partner tool — is not what this product needs, so the Account from ADR-0008 is the only identity, and Cloudflare's role is the network in front of the origin.
- **The origin sits behind Cloudflare's proxy, and one choice there needs a deliberate answer.** A **proxied DNS record** preserves the visitor's IP at the origin; a **Cloudflare Tunnel** (free on all plans) removes the origin's public address entirely but sends **no visitor IP at all**, because requests reach the origin internally. If the API ever needs to rate-limit or attribute a request by client, the proxied path is the one that keeps that information, and if the Worker proxies the call itself the origin cannot trust `CF-Connecting-IP` either. The decision is recorded here; the mechanism belongs to the ticket that first needs it.
- **The server is a second deployable in the same repository** (`server/`), importing the domain types from `src/domain/types.ts` rather than copying them. The repo has already been bitten by a duplicated spec (`docs/spec/0002` drifted from the code), and a workspace boundary for one shared file would cost a build step and a publish path for nothing.
- **This introduces the repo's first runtime secret and its first environment read.** `grep -rn 'import.meta.env' src/` returns nothing today, CI has no deploy step, and the deploy config has no `main` script. The backend adds all three, and `.gitignore` already anticipates the secret files.
- **Feature gating is reach, not capability.** Signing in buys cross-device access, recovery, and features that genuinely need a server (a shareable bracket link, collaboration, cross-tournament stats). No existing feature is withheld from a guest, because the guest path is the product's own funnel ("No friction — the path from 'import roster' to 'split into 4 teams' has no dead ends", `PRODUCT.md`).
